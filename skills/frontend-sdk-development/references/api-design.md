# 공개 API 설계: 쓰기 쉬운 인터페이스

## "쓰기 쉽다"의 재정의

SDK의 첫인상은 도입 여부만 정하지 않는다. 이후의 확장성과 오래 쓸 수 있는지까지 결정한다.
그런데 "쓰기 쉽다"는 것은 기능이 많다는 뜻도, 코드가 짧다는 뜻도 아니다.
**잘못 쓸 수 있는 여지가 구조적으로 제거된 인터페이스**가 쓰기 쉬운 인터페이스다.

이렇게 정의해야 하는 이유: SDK 사용자(연동 개발자)의 휴먼 에러는 그 개발자만의 문제로
끝나지 않는다. 리소스 누수와 잘못된 상태는 SDK를 쓰는 플랫폼 전체의 안정성 문제가 된다.
인터페이스 자체가 안전 장치여야 한다.

## 나쁜 설계가 장애가 되는 경로

실시간 연결을 다루는 SDK를 예로 들면:

```ts
// 나쁜 예: 원자적 절차를 사용자에게 전가
const { serverId } = await sdk.server.open();

sdk.server.onConnect(`connection:${serverId}`, (connection) => {
	sdk.server.onMessage(`message:${connection.id}`, onMessage);
	sdk.server.onError(`error:${connection.id}`, onError);
});

// 정리는 순서가 중요하지만 아무도 강제하지 않는다
await sdk.server.disconnectMessages(serverId);
await sdk.server.close(serverId);
```

표면적으로는 "쓰기 어렵지 않은" API다. 문제는 지켜야 할 규칙이 암묵적이라는 것이다.

- `onConnect` 이후 `onMessage`를 부착하지 않으면 메시지가 유실된다.
- `disconnectMessages`를 빠뜨리고 `close`만 하면 리스너가 누적되고 메모리가 샌다.
- 정리 순서를 바꾸면 무엇이 일어날지 정의되어 있지 않다.

이 실수들은 컴파일 에러도, 즉각적인 런타임 에러도 내지 않는다. 조용히 쌓이다가
프로덕션에서 터진다. 그리고 그 장애는 "연동사의 실수"가 아니라 "SDK의 설계 결함"이다.

```ts
// 좋은 예: 의도 단위 API + 핸들
const server = await sdk.start({ onConnection, onMessage });

// 정리는 한 번의 호출로 끝난다
await server.stop();
```

## 퍼사드(Facade)의 재정의

통상적 정의는 "복잡한 서브시스템을 단순한 인터페이스로 감싸는 패턴"이다. 이 정의로는 부족하다.
SDK에서 퍼사드의 본질은 기능을 숨기는 것이 아니라, **복잡한 내부 구현을 '사용자의 의도(intent)'
기준으로 다시 구성하는 것**이다.

내부에는 인증, 재시도, 상태 관리, 클린업 같은 복잡한 요소가 있지만, 사용자는
"서버를 시작한다", "파일을 업로드한다", "결제를 요청한다"라는 자연스러운 목적만 표현하면 된다.

참고할 만한 선례가 인프라 도구의 추상화 레벨 구조다. AWS CDK는 모든 속성을 세밀하게
제어하는 L1(관리 부담이 크다)과 의도 기반으로 흔한 유즈케이스를 한 번에 처리하는
L2를 함께 제공한다:

```ts
// L1: 모든 설정을 직접 제어한다. 세밀하지만 무겁다
new CfnBucket(this, 'MyBucket', {
	bucketName: 'my-bucket',
	versioningConfiguration: { status: 'Enabled' },
	publicAccessBlockConfiguration: {/* ... */}
});

// L2: 의도 기반이라 흔한 유즈케이스를 한 줄로 쓴다
new Bucket(this, 'MyBucket', { versioned: true });
```

L2는 내부적으로 필요한 모든 설정을 자동 변환하고 권한과 알림 같은 주변 구성도
자연스러운 API로 제공한다. SDK도 같은 구조를 가져야 한다.

## 의도 기반 API 규칙

1. **메서드 이름은 사용자의 목적을 말한다.** 고수준 API에서 `open`/`listen`/`dispose` 같은
   내부 절차 이름을 노출하지 마라. `start`/`stop`, `requestPayment`, `upload`처럼
   사용자가 이루려는 일의 이름을 붙여라.
2. **하나의 의도 호출이 필요한 절차를 전부 오케스트레이션한다.**

    | 사용자 호출        | 내부에서 일어나는 일                                       |
    | ------------------ | ---------------------------------------------------------- |
    | `sdk.start({...})` | 연결을 열고 모든 이벤트 리스너를 등록한 뒤 핸들을 반환한다 |
    | `handle.stop()`    | 모든 리스너를 해제하고 연결을 닫아 정리를 끝낸다           |

    사용자는 생명주기를 생각할 필요가 없고, 리소스 누수는 원천적으로 불가능해진다.

3. **리소스를 만든 곳이 정리를 책임진다.** 생성 API가 반환한 핸들이 정리 메서드를 가진다.
   "이건 사용자가 알아서 해제해야 한다"가 남아 있다면 설계가 덜 끝난 것이다.

## 고수준 API와 저수준 API의 공존 (80/20)

좋은 SDK는 퍼사드만 제공하지 않는다. 파레토 법칙으로 계층을 나눠라.

- **반복적인 공통 유즈케이스 80%**: 고수준 퍼사드로 처리
- **특수한 요구 20%**: 저수준 API로 내려갈 수 있는 탈출구(escape hatch) 제공

```ts
// High-level: 대부분의 경우
const server = await sdk.start({ onConnection, onMessage });

// Low-level: 특수 케이스. 예를 들어 특정 연결만 유지하고 나머지는 끊는다
const serverId = await sdk.server.open();
sdk.server.onConnect(`connection:${serverId}`, (conn) => {
	if (shouldKeep(conn)) {
		sdk.server.onMessage(`message:${conn.id}`, onMessage);
	}
});
```

이 저수준 API는 앞의 '나쁜 예'와 같은 형태지만 성격이 다르다. **유일한 인터페이스로
강요되면 설계 결함이고, 안전한 고수준 기본값 옆에 문서화된 탈출구로 제공되면 정당한
선택지다.**

이 구조의 세 가지 효과:

1. **단기 DX**: 대다수 개발자는 간단한 고수준 API 몇 줄로 끝난다.
2. **성능과 안정성**: 오케스트레이션 로직을 SDK가 통제하므로 최적화와 안전장치를
   일괄 적용할 수 있다.
3. **장기 호환성**: 내부 구현이 바뀌어도 저수준 API를 안정적으로 유지하면
   breaking change를 피할 수 있다.

## 트레이드오프와 운영

퍼사드 전략에는 비용이 있다. 알고 감수하는 것과 모르고 당하는 것은 다르다.

- **덮지 못하는 요구는 반드시 나온다.** 고수준 추상화는 특정 방식만 지원하도록 설계되므로,
  escape hatch가 없으면 특수 요구가 SDK 수정 요청과 포크, 내부 API 해킹으로 이어진다.
- **오케스트레이션 유지 비용은 SDK 개발자의 몫이다.** SDK가 성숙할수록 내부는 복잡해지고
  사용자 코드는 단순해져야 정상이다. 반대로 가고 있다면(사용자 코드가 점점 복잡해진다면)
  퍼사드가 제 역할을 못 하는 것이다.
- **"무엇이 80%인가"는 고정이 아니다.** 사용 데이터와 문의 내용을 근거로, 어떤 기능을
  퍼사드에 포함할지 계속 재평가하라. 저수준 API 사용 패턴이 반복되면 그것이 다음
  고수준 API 후보다.

## 체크리스트

- [ ] 대표 유즈케이스가 고수준 API 3~5줄로 끝나는가
- [ ] 호출 순서 실수와 정리 누락이 구조적으로 불가능한가 (틀릴 수 있는 절차가 남아 있다면 불합격)
- [ ] 리소스를 만든 API가 반환한 핸들이 정리까지 책임지는가
- [ ] 고수준으로 안 풀리는 요구를 저수준 API 조합으로 풀 수 있는가
- [ ] 고수준 메서드 이름이 내부 절차가 아니라 사용자 의도를 말하는가
- [ ] 저수준 API의 반복 사용 패턴을 다음 고수준 API 후보로 추적하고 있는가
