# 변경 프로세스

## 구현 전 확인

1. **기존 코드를 읽는다.** 수정 대상과 직접 연관된 파일(상속, import, 이벤트 구독)을 먼저 연다. 추측으로 고치지 않는다
2. **계약을 확인한다.** 요구사항과 공개 계약의 정본이 어디인지 먼저 찾는다. 정본과 코드가 어긋나면 `autonomy.md`를 적용해 사용자 확인을 받는다
3. **공개 계약 영향을 판단한다.** 외부에 노출되는 타입이나 시그니처를 건드리면 공개 API 변경이고 사용자 승인이 필요하다
4. **테스트를 확인한다.** 기존 테스트가 있는지, 변경으로 깨지는지. TDD 원칙은 `testing.md`

## 구현 후 게이트

프로젝트가 정한 검사를 전부 통과해야 완료다. 순서는 **빠른 실패 먼저**로 잡는다. 타입 검사가 가장 싸고 lint 피드백이 가장 늦다.

타입 검사를 먼저 돌리고 빌드와 테스트를 지나 린트로 끝낸다.

하나라도 실패하면 커밋하지 않는다. 한 패키지 안에서 끝나는 변경이면 대상을 좁혀 빠르게 돌린다.

## 게이트를 통과시키는 방법

게이트를 통과시키려고 테스트를 skip하거나 lint 규칙을 끄거나 assert를 느슨하게 고치지 않는다. 그것은 게이트를 통과한 것이 아니라 게이트를 치운 것이다.

## 완료 판정

- 게이트 전부 통과
- 통합 검증 통과: 경계면 교차 비교(공개 타입과 실제 값, 어댑터 시그니처, 프로토콜 상수와 발행 코드)
- 공개 API를 바꿨으면 관련 문서를 함께 갱신
- 증거 없는 통과 표시는 하지 않는다

## 롤백 기준

같은 게이트가 **3회 이상** 반복 실패하고 원인이 설계 오판이나 계약 오독처럼 근본에 있으면:

1. 변경을 시작 직전 상태로 되돌린다
2. 설계 단계로 돌아가 원인을 다시 본다
3. 계약 해석이 의심되면 정본에서 재확인한다

4회차를 시도하지 않는다. 같은 방법으로 네 번째도 실패한다.
