# 테스트 규칙

## TDD 원칙

- **버그 수정은 재현 테스트부터.** 실패하는 테스트를 먼저 쓰고 통과시킨다. 예외 없다
- **신규 공개 API는 테스트로 먼저 설계한다.** 시그니처, 에러 경로, 이벤트를 테스트에 적고 구현한다
- **리팩토링 전에 기존 동작을 덮는 테스트가 있는지 확인한다.** 없으면 characterization test를 먼저 쓴다

## 무엇을 반드시 테스트하는가

공개 계약이 우선이다. 타입 검사가 닿지 않는 경계일수록 런타임 방어가 실제 안전장치다.

- 공개 진입점의 런타임 검증: 잘못된 값이 필드 단위 정보와 함께 거부되는가
- 에러 코드 매핑: 어떤 실패가 어떤 코드가 되는가
- 이벤트: 이름과 페이로드가 계약대로인가, 발행 시점이 맞는가
- 프로토콜 상수: 정본 문서의 레지스트리와 일치하는가
- 상태 전이: 도달 불가능한 상태가 없고, 갱신이 누락된 전이가 없는가

자명한 동작에는 테스트를 두지 않는다. `typeof` 검사, 재수출 이름의 존재 확인, 언어와 타깃이 보장하는 동작(instanceof 판별), 테스트 파일 안의 배열 길이를 스스로 세는 검사가 그렇다. 이런 테스트는 실패할 방법이 없거나 실패해도 제품 결함을 가리키지 않는다.

## Mock 정책

| 대상                                              | Mock                                |
| ------------------------------------------------- | ----------------------------------- |
| 외부 서비스 어댑터(네트워크, 스토리지, 외부 API)  | 허용. 단위와 통합에서 페이크로 대체 |
| 브라우저 API(`getUserMedia`, `RTCPeerConnection`) | 허용. 테스트 환경에 없다            |
| 도메인 로직(오케스트레이션, 상태 전이, 검증)      | **금지**                            |
| 처리 파이프라인 체인 전체                         | 개별 단계만 허용, 체인은 실물       |

도메인을 mock으로 채우면 실제 규칙 위반이 테스트를 통과한다. 도메인 경계는 실물로 검증한다.

여러 테스트가 나눠 쓰는 페이크는 그 패키지의 `src/testing/`에 둔다. 공개 진입점에서는 재수출하지 않는다. 테스트 지원 코드지 모듈의 계약이 아니다.

## 커버리지

수치보다 **무엇이 덮였는가**가 먼저다. 위의 "반드시 테스트하는 것" 목록이 실질 기준이다. 수치 게이트를 두려면 그 목록이 먼저 채워진 다음이다.

## 파일 명명

- 단위: `{source}.test.ts`
- 통합: `{feature}.integration.test.ts`
- E2E: `{scenario}.e2e.test.ts`

한 파일에 한 주제. `describe` 중첩은 3단계 이내.

## Flaky 테스트

1. `describe.skip`으로 감추지 않는다. `test.fixme`를 쓰고 재현 조건을 적는다
2. 근본 원인을 특정한다: 타이밍 race인지, 네트워크인지, DOM 상태인지
3. 24시간 안에 고치거나 일감을 만든다

`test.retry(N)`로 덮지 않는다. 감춰진 race는 운영 중에 터진다.

## 금지 패턴

1. `test.only` 커밋: CI에서 한 케이스만 돌아가는 사고를 만든다
2. 하드코딩된 sleep(`await new Promise(r => setTimeout(r, 500))`): 이벤트나 조건 대기로 대체한다
3. 테스트 순서 의존: 각 테스트는 독립 실행 가능해야 한다
4. 프로덕션 서버를 향한 테스트: 개발이나 QA 환경만 쓴다
5. 통과시키려고 assert를 느슨하게 고치기: 그것은 테스트를 지운 것이다
