# 오류를 감추지 않는다

## 규칙

**오류를 감싸 빈 값이나 기본값을 돌려주고 호출자에게 성공한 것처럼 보이게 하지 않는다.** 증상을 가리는 임시 우회도 같다. 근본 원인을 고친다.

빈 배열과 빈 문자열, 0, 빈 객체는 정상 결과와 모양이 같다. 호출자는 실패를 알 수 없다.

## 이 규칙이 생긴 이유

실패가 정상 결과와 같은 모양이 되면 그 순간에는 아무것도 깨지지 않는다. 화면이 그려지고 빌드가 통과하고 배포가 나간다. 실패는 며칠 뒤에 전혀 다른 증상으로 돌아오고 그때는 어디서 실패했는지 추적할 로그도 없다. 우회를 쌓으면 실제 결함이 본 함수가 아니라 우회 경로에 숨는다.

감싸고 싶어지는 곳은 설계가 틀린 곳인 경우가 많다. 런타임에 실패할 수 있는 읽기를 빌드 타임으로 옮기거나 실패를 타입에 드러내면 감쌀 것 자체가 없어진다.

## 금지하는 것

**실패를 정상 결과와 같은 모양으로 만드는 코드.**

```ts
async function fetchItems(area: string): Promise<Item[]> {
	try {
		const res = await fetch(`/api/items?area=${encodeURIComponent(area)}`);
		return (await res.json()).items;
	} catch {
		return [];
	}
}
```

항목이 없는 상태와 서버를 못 읽은 상태가 같은 값이 된다.

- **비어 있는 catch.** `catch {}`와 `catch (e) { /* ignore */ }`. 무엇이 실패했는지 아무 데도 남지 않는다
- **파싱 실패를 그럴듯한 기본값으로 메우기.** 깨진 입력으로 들어온 사용자가 자기가 고른 것과 다른 조건으로 결과를 받는다
- **없는 값을 흘려보내기.** `data?.user?.profile?.name ?? ''`처럼 물음표를 이어 붙이면 어느 단계가 비었는지 사라진다. 데이터 계약을 타입으로 강제하거나 응답을 정규화하는 곳에서 잡는다
- **setTimeout과 setInterval로 타이밍을 피하기.** 이벤트, Promise 체인, 상태 구독처럼 정상적인 동기화로 바꾼다. cleanup 누락을 늦은 setTimeout으로 덮는 것도 같다. cleanup 함수나 AbortSignal로 푼다
- **한도 없는 재시도.** backoff와 횟수 제한, 멱등성 없는 재시도는 장애를 키운다
- **플래그로 가르기.** `if (FEATURE_X_BROKEN)`, `if (process.env.WORKAROUND)`. 본질을 고치고 플래그를 지우는 것까지가 작업이다
- **이름이 의도를 자백하는 것.** `fallback`, `tempFix`, `workaround`, `hack`이 들어간 함수와 변수, 파일
- **비슷한 함수 둘을 두고 한쪽이 실패하면 다른 쪽 호출.** 한 함수로 합치거나 정상 경로를 고친다
- **타입 캐스팅으로 넘어가기.** `as any`, `as unknown as T`
- **상태 흐름이 안 맞아 DOM을 직접 바꾸기.** 렌더 경로를 바로잡는다
- **임시 mock과 하드코딩한 응답을 남기기.** 이번 작업 안에서 고치거나 별도 작업으로 나눈다

## 대신 하는 것

**실패할 수 없는 설계로 바꾼다.** 가장 먼저 볼 선택지다. 배포 시점에 정해진 값(환경 변수, 정적 설정, 라우트 목록)은 런타임에 읽어 감싸지 말고 빌드 단계에서 검증한다. 값이 없으면 빌드를 멈춘다. 틀린 화면이 나가는 것보다 배포가 멈추는 편이 낫다.

**예외를 일으킨다.** 가장 가까운 에러 경계가 받는다. 빌드 타임에 일으키면 배포가 멈춘다.

**실패를 값의 타입에 남긴다.** 실패를 값으로 돌려줘야 하면 셋을 지킨다. 이름에 적고 로그를 남기고 호출자가 분기해야 하는 타입으로 돌려준다.

```ts
async function fetchItemsOrNull(area: string): Promise<Item[] | null> {
	try {
		const res = await fetch(`/api/items?area=${encodeURIComponent(area)}`);
		if (!res.ok) {
			console.warn(`[items] GET ${area} failed: ${res.status}`);
			return null;
		}

		return (await res.json()).items;
	} catch (error) {
		console.warn(`[items] GET ${area} network error`, error);
		return null;
	}
}
```

`null`이 반환 타입에 있으니 호출자는 분기해야 한다. 로그가 있으니 무슨 일이 있었는지 남는다. 데이터 요청 라이브러리가 에러 상태를 주면 직접 감싸기 전에 그 상태로 풀 수 있는지 먼저 본다.

## 허용되는 축소 동작

기능을 줄여서 계속 동작하게 만드는 것은 감추기와 다르다. 세 조건을 전부 만족할 때만 그렇다.

| 조건                            | 뜻                                                                     |
| ------------------------------- | ---------------------------------------------------------------------- |
| 제품 결정이고 문서에 적혀 있다  | 명세나 설계 문서가 이 실패를 어떻게 보여줄지 정했다                    |
| 실패한 상태가 화면에서 구분된다 | 0이나 빈 값으로 바꾸지 않고 "모름"이나 안내 문구처럼 실패로 보여준다   |
| 실패가 로그에 남는다            | 프로젝트 로거로, 로거가 없으면 접두사를 붙인 `console.warn`으로 남긴다 |

로그가 빠지면 감춘 것이다. 화면 구분이 빠지면 틀린 값을 사실처럼 보여주는 것이다.

외부 시스템이 멈췄을 때 사용자에게 알리고 다시 연결하는 것, 브라우저 기능 검사(`'serviceWorker' in navigator`), 구 버전 응답 형식 처리, 개발 모드에서만 도는 분기도 같은 조건으로 판정한다.

**흡수한 실패가 아래 단계에서 다시 뭉개지는 곳을 조심한다.** `fetchItemsOrNull`이 `null`을 제대로 돌려줘도 그 위에서 `?? []`로 받으면 "항목 없음"과 "항목 모름"이 같아진다. `null`은 화면까지 살아가야 한다.

## 멈춰야 할 때

다음 말이 떠오르면 우회를 짜고 있다는 신호다. 멈추고 근본 원인을 본다.

- "일단 ~로 해두고 나중에", "임시로 ~ 처리"
- "이건 ~한 경우니까 그냥 빈 값", "어차피 거의 안 일어나는 경우"
- "엣지 케이스라 catch만 해두자", "race 같으니 setTimeout으로"

멈춘 뒤에는 근본 원인 가설과 정상적으로 고치는 비용을 보고한다. 범위 밖이면 별도 작업으로 나눈다.

## 리뷰에서 볼 것

- `catch` 블록이 값을 돌려주면 그 값이 정상 결과와 구분되는가
- 비어 있는 `catch`가 없는가
- `?? []`와 `?? 0`, `?? ""`가 실패를 삼키고 있지 않은가
- 새로 감싸려는 호출을 빌드 타임으로 옮길 수 있는가. 옮길 수 있으면 감싸지 말고 옮긴다
