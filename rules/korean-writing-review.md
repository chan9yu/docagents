# 한국어 글 검토

문장 규칙은 `korean-writing.md` 가 정본이다. 이 파일은 그 규칙으로 글을 고치고 검사하는 절차다.

## 비유

비유를 아예 금지하지는 않는다. 다만 고를 때 순서가 있다.

**평범한 말이 이미 있으면 비유를 쓰지 않는다.** 비유가 나쁜 것이 아니라 이상하게 쓴 비유가 나쁘다. 그 자리에 정확한 말이 있는데 굳이 비유를 얹으면 읽는 사람이 한 번 더 번역해야 한다. 공개 API를 "약속"이라 부른 자리가 그랬다. 인터페이스는 인터페이스라고 적는다.

판정은 한 문장으로 한다. **이 비유를 빼고 평범한 말로 적으면 문장이 나빠지는가.** 나빠지지 않으면 뺀다.

**정확한가보다 독자가 아는가가 먼저다.** 아무리 정확해도 독자가 그 영역을 모르면 설명할 것이 하나 늘어날 뿐이다.

**가장 좋은 것은 비유가 아니라 독자가 겪은 일이다.** 글의 주제 안에 답이 있는 경우가 많다.

**비유가 본문에서 자기 잘못을 변명하고 있으면 그 비유는 틀린 것이다.** "비유가 여기서 어긋나요"라는 문장이 필요해지면 예외를 적을 게 아니라 비유를 바꾼다.

**쉽게 쓰려다 비유가 나오면 사물 대신 동작을 적는다.** "신원"이 어렵다고 느끼면 "이름표"가 나오고 "한계"를 풀려다 "손이 모자라다"가 나온다. 필요한 것은 무엇인지가 아니라 무엇을 하는지다.

**비유를 읽고 나면 다음 문단이 더 쉬워지는지 본다.** 그림만 예쁘고 다음 문단에서 다시 처음부터 설명해야 하면 그 비유는 자리만 차지한 것이다.

금지된 비유 계열이 몇 있다. 길 은유("닿는 길이 없다", "길이 닫히다", "갈림길", "우회로"), 신체 관용구("손이 모자라다", "눈에 익다", "발을 들이다"), 의존을 물건에 빗대는 말("전부 매달려 있다", "통째로 얹혀 있다"), 코드를 세는 단위 "벌"("코드가 세 벌"은 "세 곳에 구현"으로), 상황을 가리키는 "자리"(손가락으로 짚을 수 있는 지점에만 쓴다)다. 뒤의 둘은 `korean-writing.md`의 금지 표현 목록과 아래 검사 명령에도 넣어 두었다. 이 문단에만 적어 두었을 때 실제로 새어 들어갔기 때문이다.

## 번역 은유를 만들지 않는다

영어 단어를 한국어로 옮기면 원래 담고 있던 구체성이 사라지고 은유만 남는다. 새 용어를 만들 때 가장 자주 나오는 실수다.

envelope에는 "안에 무언가를 넣어 봉한다"는 실물이 있지만 "봉투"는 그 실물을 한국어 문장에 다시 등장시킨다. 영어에서는 그 그림이 죽은 은유라 아무도 원관념을 떠올리지 않지만, 한국어로 옮기면 그림이 되살아나 읽는 사람이 원관념을 재구성해야 한다.

| 쓰지 않는 말 | 원어 | 대신 쓰는 말 |
| --- | --- | --- |
| 봉투 | envelope | 메시지 구조, 공통 필드 |
| 동봉 | bundled | 번들에 넣다, 함께 포함하다 |
| 프로브 | probe | 무엇을 재는지 그대로 적는다 |
| 배선 | wiring | 연결, 잇는다, 거는 자리 |
| 이음매 | seam | 잇는 구현, 맞물리는 자리 |
| 관문 | gate | 조건, 검사, 확인하는 자리 |
| 접기표 | fold table | 대응표 |
| 씨앗 | seed | 초기값 |
| 부작용 | side effect | 사이드 이펙트. 한국어 "부작용"은 약의 부작용처럼 나쁜 것을 뜻해서 원래 말이 담지 않은 판단이 붙는다 |
| 앞머리 막힘 | head-of-line blocking | 원어를 그대로 쓰고 무슨 일이 일어나는지는 한국어 문장으로 적는다 |
| 냄새, 코드 냄새 | code smell | 고칠 데가 보인다, 잘못 쓰기 쉽다 |
| 기술 부채 | technical debt | 나중에 고쳐야 할 것, 미뤄 둔 일 |
| 은탄환 | silver bullet | 한 번에 다 푸는 방법 |
| 깨진 창문 | broken window | 방치된 문제 |
| 고무 오리 | rubber duck | 소리 내어 설명해 보기 |
| 야크 털 깎기 | yak shaving | 곁가지 일에 매달리기 |
| 자전거 창고 | bikeshedding | 사소한 것에 말이 길어지기 |
| 행복 경로 | happy path | 정상 흐름, 잘 풀리는 경우 |

새 말을 만들기 전에 이렇게 확인한다.

- 영어 단어를 옮긴 것인가. 옮겼다면 그 자리에서 무엇이 일어나는지 동사로 적을 수 있는가
- **영어 원어를 모르는 사람이 그 한국어만 보고 뜻을 짐작할 수 있는가**
- 그 자리에 이미 평이한 말이 있는가

과시성 전문용어도 같은 이유로 쓰지 않는다. 읽는 사람이 뜻을 모르면 문장이 멈춘다.

**표에 없는 말이 새로 잡히면 표에 넣는다.** 판정 기준은 위의 두 번째 항목 하나다.

## em dash를 없애는 방법

문맥마다 다르다.

- 뒤에 오는 것이 보충 설명이면 두 문장으로 끊는다
- 짧은 삽입구면 쉼표나 괄호로 바꾼다
- 앞뒤가 인과나 대조로 이어지면 그래서, 다만, 대신 같은 접속사로 푼다
- 표 안이라 공간이 없으면 문장을 줄이거나 칸을 나눈다

어느 쪽이든 기호 하나로 뭉뚱그리던 관계를 말로 풀어 쓰게 된다. 글이 그만큼 분명해진다.

## 고칠 때 새 위반이 생긴다

금지 표현을 고치다가 다른 금지 표현을 넣는 일이 반복해서 일어난다. 실제 사례다.

| 고치려던 것 | 새로 생긴 위반 |
| --- | --- |
| "한계" | "손이 모자랍니다" (신체 관용구) |
| "신원" | "이름표" (사물 비유) |
| "셈입니다" | "못을 박는" (이미 금지 목록에 있던 말) |
| 공개 API를 부르는 말 | "약속" (평범한 말이 있는데 얹은 비유) |
| `죠` 종결 제거 | `고요` 종결 (같은 계열인데 새로 넣음) |

원인은 둘이다. 고친 문장은 정의상 검사를 거치지 않은 새 문장이고, 쉽게 쓰려는 의도가 비유를 부른다.

그래서 절차를 둔다.

- **일괄 변환 뒤에는 새로 쓴 문장만 따로 모아 다시 읽는다.** 통과시킨 문장이 아니라 고친 문장을 본다
- **지우지 말고 옮기는 실수를 조심한다.** `고요`를 다른 문장으로 옮겨 놓고 고쳤다고 착각한 적이 있다
- **새 문장이 생기는 작업을 먼저 하고 검사를 그 위에 얹는다.** 목록을 산문으로 푸는 작업은 서술어를 새로 만들어 내므로 종결어미 검사보다 먼저 한다

## 넣지 않는 것

**결정 이력의 부산물.** "(2026-07-26 사용자 결정)" 같은 표기, "문서 문구를 고쳤습니다" 같은 편집 이력, "dev 서버 재시작 후 검증했습니다" 같은 당연한 절차는 읽는 사람에게 가치가 없다.

**제출물에 없는 것을 가리키는 경로.** 작업 폴더가 `.gitignore`에 있다면 그 안의 파일을 문서가 가리키면 안 된다. 가보면 없는 링크가 된다.

**검증할 수 없는 집계 주장.** "테스트 15개 전부 통과" 같은 문장은 확인할 방법을 함께 내놓지 않으면 읽는 사람이 믿기 어렵다. 무엇을 관측했는지를 구체적으로 적는 편이 낫다.

**맥락상 드러날 필요 없는 고유명사.** 회사와 고객사 이름, 사내 시스템 이름, 사내 이슈 번호, 사내 URL은 남기지 않는다.

**이력 기록은 소급해 고치지 않는다.** 시간순 기록의 지난 항목은 그때 쓴 말이다. 고치면 무엇이 언제 쓰인 말인지가 사라진다. 현재 상태를 서술하는 문서와 코드 주석, 테스트 이름만 고친다.

## 도구가 만든 흔적

자동 윤문 도구를 쓴다면 결과를 그대로 믿지 않는다. 도구가 본문 끝에 자기 메타데이터를 주석으로 심거나, 표의 행을 통째로 지우거나, 인용해야 할 원문 표현을 임의로 바꾸는 일이 실제로 일어난다. 도구의 보고서와 파일의 실제 diff를 따로 대조한다.

도구에 제약을 줄 때는 바꾸지 말 것을 명시한다. 이미 여러 번 다듬은 글에 변경률 목표를 주면 멀쩡한 문장을 건드린다. 변경률이 낮아도 정상이라고 미리 알려준다.

## 검사

### 명령

저장소 루트에서 돌린다. 확장자와 제외 경로는 프로젝트에 맞게 바꾼다.

```bash
grep -rn '—\|·\|→\|↔' --include='*.md' .
find . -name '*.md' -not -path '*/node_modules/*' -print0 | xargs -0 perl -CSD -Mutf8 -ne 'print "$ARGV:$.: $_" if /[\x{1F300}-\x{1FAFF}\x{2705}\x{274C}\x{26A0}]/; close ARGV if eof'
find . -name '*.md' -not -path '*/node_modules/*' -print0 | xargs -0 perl -CSD -Mutf8 -ne 'print "$ARGV:$.: $_" if /[\x{4E00}-\x{9FFF}]/; close ARGV if eof'
grep -rn '따라서\|결론적으로\|이를 통해' --include='*.md' .
grep -rn '전자는\|전자가\|후자는\|후자가' --include='*.md' .
grep -rn '셈입니다\|셈이에요\|쓸모가 있\|몫이 됩니다\|부작용' --include='*.md' .
grep -rn '한 벌\|두 벌\|세 벌\|교과서\|정석\|되풀이\|영감을 주\|먹힌다\|효자\|한몫\|갈래\|매달려\|얹혀' --include='*.md' .
git log --format='%h %s%n%b' | perl -CSD -Mutf8 -ne 'print if /[\x{4E00}-\x{9FFF}]/'
```

이모지와 한자는 `grep -P` 대신 perl로 찾는다. macOS 기본 grep은 `-P`를 받지 않고 오류로 끝나는데, 종료 코드를 보지 않으면 0건 통과와 구분되지 않는다.

한자는 커밋 메시지에서 새어 나가기 쉬워 검사를 둘로 나눈다. 파일 검사는 저장소를 훑고 로그 검사는 이미 쌓인 메시지를 훑는다.

결과에서 걸러낼 것이 있다. 금지 표기를 금지한다고 적은 문서 자신, 시간순 이력의 날짜, 코드 블록과 표 구분선은 남긴다. 헤딩의 기호는 앵커가 걸려 있을 수 있으니 링크를 먼저 확인하고 고친다.

### 정규식 함정

계측이 재현되는 것과 계측이 맞는 것은 다르다. 아래는 실제로 틀렸던 경우다.

1. **긴 패턴이 짧은 패턴을 삼킨다.** `[가-힣]다[.!?]`로 평서체를 세면 "습니다"와 "입니다"가 같이 잡혀 오측한다. 긴 것부터 빼낸다
2. **어간이 활용에서 변한다.** `견주`로 찾으면 "견줍니다"를 놓친다. 활용형을 나열한다(`견주|견줍|견줘`)
3. **짧은 패턴이 다른 형태소를 삼킨다.** `고요[.!?]`로 나열 연결어미를 찾으면 "-더라고요"가 함께 잡힌다. 둘은 다른 형태소이고 뒤엣것은 자연스러운 말이다. 앞을 배제하는 조건을 붙인다(`(?<!더라)고요[.!?]`)
4. **조사가 받침에 따라 갈린다.** `를 듭니다`로 찾으면 "값을 듭니다"를 놓친다(`[을를] 듭니다`)

패턴을 만든 뒤에는 **실제 위반 문장으로 잡히는지 시험한다.** 0건이 통과인지 검사 누락인지 구분되지 않는다.

### 산문에만 적은 금지어는 지켜지지 않는다

이 파일 비유 절의 산문에 "벌"과 "자리"를 금지해 두었는데도 글에 그대로 새어 들어갔다. 표와 검사 명령에는 없었기 때문이다. 기계가 못 잡으면 사람도 놓친다.

그래서 금지어를 새로 정하면 세 곳에 전부 넣는다. **설명은 산문에, 목록은 표에, 패턴은 검사 명령에** 둔다. 셋 중 하나라도 빠지면 다음에 같은 말을 또 쓴다.

**규칙에 추가하는 것과 이번 글에서 걷어내는 것은 다른 일이다.** 추가만 하고 검사를 안 돌리면 지금 고치는 글에는 그대로 남는다. 규칙을 고쳤으면 그 자리에서 검사를 다시 돌린다.

### 기준선을 믿지 않는다

비교 대상이 틀리면 측정이 정확해도 판정이 틀린다. 실제로 셋 다 겪었다.

- 문서에 적힌 기준값을 그대로 믿었다가 틀렸다. 기준이 되는 글을 **그 자리에서 다시 재라**
- 고치기 전 대상의 수치를 목표로 삼았다. 위반 상태의 수치는 위반의 결과이지 지킬 성질이 아니다
- 검사 목록에서 빠진 항목은 0건 통과와 겉보기가 같다. 스캔 표에 항목 자체가 있는지 본다

### 기계가 못 잡는 것

기계 검사가 잡는 것은 절반이다. 비유와 쉼표 판단, 명사 압축, 자기 평가는 소리 내어 읽는 검토로만 걸린다.

**그림 속 글자는 `grep`에 잡히지 않는다.** 다이어그램의 오타와 미설명 용어, 본문과 다른 이름이 발행 뒤에도 살아남는 이유다. 시각 자산은 사람이 확대해 읽는 절차를 따로 둔다.
