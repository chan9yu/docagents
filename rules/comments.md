# 주석 규칙

## 총량이 먼저다

쓰고 싶은 주석의 백 줄 가운데 한두 줄만 남긴다. 나머지는 전부 지운다.

아래 절들이 "이런 자리에는 쓴다"고 허용하는 것을 읽고 허가로 받아들이면 안 된다. 그 허용은 좁은 예외이고 기본값은 0이다. 쓰려는 충동이 들 때 스스로 "이건 비자명하니까 남긴다"고 판정하는 순간 규칙은 무력해진다. 그 판정은 쓰는 사람이 자기에게 내주는 통과 도장이라 언제나 통과한다.

작업을 마치면 diff에 주석이 몇 줄 들어갔는지 센다. 코드 백 줄에 주석 두 줄을 넘겼으면 대부분을 잘못 남긴 것이다.

지적을 받고 그 자리만 지우는 것으로는 끝나지 않는다. 다음 파일에서 같은 일이 반복된다.

## 타입 선언 안에 쓴다

인터페이스 필드와 유니온 멤버에 그 값이 무엇인지 한 줄로 적는다. 이름만으로는 개별 값의 의미가 드러나지 않는 자리다.

```typescript
export type ConnectionErrorCode =
	| 'INVALID_OPTIONS' // 팩토리 옵션 검증 실패
	| 'CONNECT_REJECTED' // 서버가 자격을 거절
	| 'SEND_FAILED';

export interface ConnectionOptions {
	/** 서버가 받는 프로토콜 식별. 서버마다 값이 달라 기본값을 두지 않는다 */
	protocol: ProtocolIdentity;
	/** 응답 대기 시간. 기본 30000 */
	connectTimeoutMs?: number;
}
```

기본값과 단위, 범위, 협의 상태처럼 타입에 담기지 않는 정보를 적는다. 필드 이름을 한국어로 옮겨 적는 것은 주석이 아니다.

## 선언부에는 쓰고 본문에는 쓰지 않는다

함수와 클래스, 메서드의 선언부 JSDoc은 이름과 타입으로 표현되지 않는 것을 담을 때 쓴다. 순서 제약(발행은 핸들러가 선 다음이어야 한다는 종류), 실측으로 확정한 값의 근거, throw 조건과 에러 코드가 그런 정보다. 이름을 한국어로 되풀이하기만 하는 JSDoc은 쓰지 않는다.

본문 안에는 쓰지 않는다. 단계 설명과 블록 해설은 이름과 구조로 말하고, 근거가 필요하면 그 코드가 속한 선언부 JSDoc으로 올린다.

지시문만 예외다. 지우면 lint나 빌드가 깨지므로 설명이 아니라 코드다.

- `// eslint-disable-next-line`
- `// @ts-expect-error`
- `/// <reference types="..." />`

## 다른 문서를 가리키지 않는다

`(정본: docs/PROTOCOL.md 4절)` 같은 문장을 쓰지 않는다. 문서가 움직이면 주석이 거짓이 되고 읽는 사람은 답을 얻으려고 코드를 떠나야 한다. 절 번호와 파일 경로, 일감 번호, 호출자 이름이 모두 같다.

값의 근거를 남겨야 하면 커밋 메시지에 적는다. git blame이 코드와 함께 따라온다.

## 설명이 필요해 보일 때

| 느낌                              | 해법                           |
| --------------------------------- | ------------------------------ |
| 이 조건이 왜 이런지 알려야 한다   | 조건을 이름 있는 변수로 뽑는다 |
| 이 숫자가 무엇인지 알려야 한다    | 이름 붙인 상수로 만든다        |
| 이 블록이 하는 일을 알려야 한다   | 함수로 뽑고 이름을 붙인다      |
| 이 예외를 왜 삼키는지 알려야 한다 | catch가 하는 일을 코드로 쓴다  |

## 소비자에게 갈 사용법

공개 API의 사용법과 예제, 발생 이벤트, 에러 목록은 코드가 아니라 문서 사이트가 담당한다. 함수에 JSDoc으로 같은 말을 두 번 쓰면 한쪽이 먼저 낡는다.
