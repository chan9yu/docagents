# 안정성과 관측 가능성: 예측 불가능한 환경에서 살아남기

## 방어적 코딩 원칙

SDK의 실행 환경에 대해 유일하게 안전한 가정은 "아무것도 가정할 수 없다"이다.
사용자 코드가 SDK를 어떻게 부를지는 상상을 초과한다.

### 1. 입력을 신뢰하지 마라

string으로 선언한 파라미터에 number가 들어온다. 실제 사고 패턴:

```ts
// 보안키 오입력을 막으려고 추가한 검증 코드가
function isSecretKey(value: string) {
	return value.startsWith('demo_secret_') || value.startsWith('real_secret_');
}
// number를 넘기는 고객사를 만나 그 자체로 장애가 됐다:
// TypeError: value.startsWith is not a function
```

검증 코드조차 입력 타입을 가정하면 장애 원인이 된다. 모든 공개 진입점에서
런타임 스키마 검증을 먼저 통과시켜라(contract-and-docs.md '런타임 검증 계층' 절).
검증 이후의 내부 코드만 타입을 신뢰할 수 있다.

### 2. 호출 빈도를 가정하지 마라

실제 사고 패턴: 사용량 분석을 위해 상태 조회 메서드에 로그 전송을 추가했다.
그런데 어떤 고객사는 그 메서드를 매우 짧은 간격으로 반복 호출하고 있었다.
호출마다 네트워크 요청이 발생하자 브라우저에 요청이 적체됐고, 페이지가 다운됐다.

- 조회용 메서드도 폴링으로 초당 수십 번 불릴 수 있다.
- 공개 메서드에 부수효과(네트워크와 저장, 로그)를 추가할 때는 **최악의 호출 패턴**을
  전제로 판단하라. 필요하면 샘플링과 배칭, 스로틀링을 SDK 내부에서 처리하라.
- "개발 편의를 위한 작은 변경"이 고객사의 비즈니스를 멈출 수 있다는 감각이
  SDK 개발의 기본기다.

### 3. 부가 기능의 실패가 핵심 기능을 죽이게 하지 마라

로깅과 분석, 모니터링 같은 부가 기능은 실패해도 조용히 넘어가야 한다(fail silently).
반대로 핵심 기능의 실패는 계약에 명세된 에러로 명확하게 드러나야 한다.
이 둘을 구분하지 않으면 로그 서버 장애가 결제 장애가 되는 어이없는 사고가 난다.

## 테스트 전략

두 층위로 나눠 촘촘하게 유지한다.

- **비즈니스 로직 단위 테스트**: 도메인 계층이 인터페이스(포트)에만 의존하면
  목(mock)을 꽂는 것만으로 정책과 유스케이스를 단독 검증할 수 있다(architecture.md 참고).
  아키텍처가 좋으면 테스트가 싸진다.
- **연동 흐름 E2E 테스트**: 사용자가 실제로 겪는 시나리오를 실제 브라우저 환경에서 검증한다.
  SDK를 로드해 초기화하고 호출해서 결과를 받기까지가 그 시나리오다. SDK 버그의 다수는 단위가 아니라
  경계(브라우저 API, 통신, 생명주기)에서 나온다.

규모 감각: 수많은 연동 코드가 걸린 핵심 흐름을 다루는 SDK라면 단위 테스트와
E2E 통합 테스트를 각각 수백 개 규모로 유지하는 것이 과하지 않다. 테스트는 비용이
아니라 "고객사 코드에 박혀 되돌릴 수 없는 배포"에 대한 보험이다.

다만 SDK는 테스트만으로 충분하지 않다. 테스트는 내가 예상한 시나리오만 검증한다.
예상 밖 환경에서 오는 문제는 다음 절의 모니터링이 잡는다.

## 흐름 전체를 관통하는 Trace ID

장애 문의가 오면 "어느 고객사의 어느 요청이 어디서 죽었는지"를 찾아야 한다.
프론트엔드 로그와 백엔드 로그가 따로 놀면 이 추적에 시간이 오래 걸린다.

해법: 결제 요청부터 완료까지, 인증 시작부터 토큰 발급까지, 업로드 시작부터 완료까지 같은
핵심 흐름의 시작 시점에 **global trace id**를 발급하고
프론트엔드와 백엔드 구분 없이 흐름의 모든 로그에 포함시켜라.
식별자 하나로 시스템 레이어 전체를 관통해 추적할 수 있어야 한다.

## 입구-출구 매핑 모니터링

개별 로그를 쌓는 것을 넘어, 흐름의 **시작 로그(입구)와 완료 로그(출구)를 매핑**해
성공률을 산출하라. 두 개의 축으로 나눠 보는 것이 핵심이다:

- **연동 주체별**(고객사와 앱, API 키 등 배포 모델에 맞는 단위): 전체 평균은 정상인데
  특정 연동 주체만 0%로 떨어지는 장애가 흔하다. 집계 평균은 이런 장애를 숨긴다.
- **런타임 환경별**: PC 브라우저와 Android WebView, iOS WebView는 사실상 서로 다른 환경이다.
  특정 환경에서만 죽는 문제를 분리해서 봐야 한다.

이 지표를 CLI나 대시보드로 만들어 **배포 루틴에 포함**시키고 임계치 기반 자동 얼럿을
더해 사람이 지켜보지 않을 때도 급감을 감지하게 하라. 실제 운영 사례:
배포 직후 특정 고객사의 성공 건수가 수십 건에서 0건으로 급감한 것을 이런 도구로 즉시
감지해 대응했다. 배포 전후 비교가 가능한 형태여야 한다는 뜻이다.

배포 직후가 최고 위험 구간인 이유: SDK의 변경은 수백 고객사의 프로덕션에 동시에
적용된다. 문제를 감지하는 속도가 곧 장애의 크기를 결정한다.

## 장애 대응 루틴 (SKILL.md의 'SDK 장애와 버그를 분석할 때' 상세)

1. **환경부터 특정한다**: 어떤 브라우저나 웹뷰인가? 입력값의 실제 타입은? 호출 빈도는?
   SDK 버그의 다수는 코드가 아니라 "예상 밖 환경과 입력, 호출 패턴"에서 온다.
2. **trace id로 구간을 좁힌다**: 시작 로그는 있는데 완료 로그가 없다면, 그 사이
   어느 레이어에서 끊겼는지 trace로 따라간다.
3. **구조적 재발 방지를 묻는다**: 수정으로 끝내지 말고 반드시 질문하라.
   같은 유형의 사고를 개인의 주의가 아니라 구조(런타임 검증, 인터페이스 설계,
   모니터링)로 막을 수 있는가? 사고는 어느 구조를 고쳐야 하는지 알려주는 신호다.

## 체크리스트

- [ ] 모든 공개 진입점이 런타임 검증을 통과한 뒤에만 내부 로직에 도달하는가
- [ ] 공개 메서드의 부수효과가 고빈도 호출을 견디는가 (샘플링과 배칭, 스로틀링)
- [ ] 부가 기능(로깅과 분석)의 실패가 핵심 기능과 격리되어 있는가
- [ ] 도메인 로직이 목만으로 단위 테스트되는가
- [ ] 실제 브라우저와 웹뷰에서 도는 연동 흐름 E2E가 있는가
- [ ] 핵심 흐름을 trace id 하나로 전 레이어 추적할 수 있는가
- [ ] 연동 주체별 성공률과 환경별 성공률을 배포 전후로 비교하고 임계치로 자동 얼럿을 받는가
- [ ] 장애 수정 후 "구조로 막을 수 있었는가"를 물었는가
