# 프론트엔드 SDK 개발

## SDK는 왜 다르게 만들어야 하는가

일반 프론트엔드 앱은 내가 배포하고 내가 실행 환경을 통제한다. SDK는 정반대다.
**남의 코드 속에 박혀, 남의 환경에서, 남의 수명으로 실행된다.** SDK 개발의 모든 제약은 이 한 문장에서 파생된다.

- **수명을 공유한다.** 사용자는 연동을 마치면 그 코드를 몇 년씩 건드리지 않는다. 한 번 공개한
  인터페이스는 사실상 계약이며, 마음대로 바꾸거나 없앨 수 없다.
- **런타임을 통제할 수 없다.** 어떤 브라우저와 웹뷰, 프레임워크에서, 어떤 타입의 값으로, 얼마나
  자주 호출될지 알 수 없다. 타입 선언은 외부 호출자를 구속하지 못한다.
- **사용자의 실수는 곧 나의 장애다.** 연동 개발자의 휴먼 에러를 "쓰는 쪽 잘못"으로 돌릴 수 없다.
  잘못 쓰기 어려운 인터페이스를 만드는 것까지가 SDK 개발자의 일이다.

실제로 반복되는 사고의 전형 두 가지가 이 특수성을 보여준다.

| 사고                                                           | 원인                                                                              | 교훈                                                                                                         |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 조회 메서드에 사용량 로그 전송을 추가했더니 서비스 페이지 다운 | 어떤 고객사가 그 메서드를 매우 짧은 간격으로 반복 호출해 네트워크 요청이 적체됐다 | 공개 메서드의 호출 빈도와 방식은 내가 정하는 것이 아니다. 부수효과 추가는 최악의 호출 패턴을 전제로 판단하라 |
| `value.startsWith(...)` 보안 검증을 넣었더니 런타임 에러       | string으로 선언한 파라미터에 number를 넘기는 고객사가 존재                        | 타입 시그니처를 믿지 마라. 공개 API 진입점에서는 런타임 검증이 필수다                                        |

## 이 스킬을 쓰지 않을 때

프로젝트에 개발 오케스트레이터가 따로 있으면 마일스톤 단위 작업은 그쪽이 먼저 받는다. 이 스킬은 공개 API의 형태와 호환성을 판단해야 할 때 쓴다.

남이 만든 SDK를 가져다 붙이는 연동 작업, 밖으로 노출되지 않는 앱 내부 코드를 정리하는 작업에는 쓰지 않는다.

## 4가지 설계 가치

SDK에 관한 모든 설계와 리뷰, 수정 판단은 다음 4가지 가치로 환원된다.
각 가치의 심화 내용과 코드 예시는 references/ 파일에 있다.

| 가치       | 핵심 질문                                                            | 상세                                   |
| ---------- | -------------------------------------------------------------------- | -------------------------------------- |
| **사용성** | 잘못 쓰기 어렵고, 대표 유즈케이스가 몇 줄로 끝나는가?                | references/api-design.md               |
| **안정성** | 최악의 환경과 입력, 호출 패턴에서도 살아남고 이상을 즉시 감지하는가? | references/stability-and-monitoring.md |
| **확장성** | 고객별 요구를 표준 코드 오염 없이 수용할 수 있는가?                  | references/architecture.md             |
| **명확성** | 인터페이스만 보고 연동할 수 있고, 변경의 이유를 추적할 수 있는가?    | references/contract-and-docs.md        |

### 사용성: 올바른 사용을 구조로 강제하라

"쓰기 쉬운 SDK"는 기능이 많거나 코드가 짧은 SDK가 아니다.
**올바르게 쓸 수밖에 없도록 구조가 유도하는 SDK**다.

- API는 원자적 절차(open, listen, cleanup, close 순서)가 아니라 **사용자의 의도 단위**(start/stop)로
  설계하라. 절차를 노출하면 연동 개발자가 순서를 외우고 정리를 챙겨야 하고, 그 실수는 결국
  플랫폼 장애로 돌아온다.
- 리소스를 만든 API가 정리까지 책임지게 하라. `start()`가 핸들을 반환하고 `handle.stop()` 하나로
  리스너 해제와 연결 종료가 전부 끝나야 한다.
- 고수준 API로 80%의 공통 유즈케이스를 덮고, 나머지 20%를 위한 **저수준 API(escape hatch)를
  함께 공개하라.** 고수준만 있으면 특수 요구에 막히고, 저수준만 있으면 모두가 위험한 조립을 반복한다.

### 안정성: 예측 불가능한 환경을 전제로 하라

- 모든 공개 API 진입점에서 런타임 스키마 검증을 수행하라. 잘못된 입력은 내부 로직에 도달하기 전에
  "어떤 필드가 왜 잘못됐는지" 말해주는 에러로 차단한다.
- 공개 메서드에 부수효과(네트워크와 로그, 저장)를 추가할 때는 고빈도 호출을 전제로 판단하라.
- 부가 기능(로깅과 분석)의 실패가 서비스 앱과 핵심 기능을 죽이게 하지 마라.
- 관측 가능성을 설계 단계에 포함하라. 흐름 전체를 관통하는 trace id를 두고, 시작 로그와 완료 로그를
  매핑해 연동 주체별(고객사와 앱) 성공률과 런타임 환경별 성공률을 내고, 배포 직후 급감을 감지한다.

### 확장성: 변경의 원인으로 경계를 그어라

- 계층은 기술 종류가 아니라 **변경이 발생하는 이유**로 나눠라. 공개 인터페이스 계층(계약 검증과 번역)과
  도메인 계층(비즈니스 로직), 외부 서비스 계층(기술 구현)이다.
- 도메인은 인터페이스에만 의존하고 구현체는 런타임에 조립하라(의존성 역전).
- 특정 고객 전용 요구는 `if (clientId === ...)` 분기가 아니라 **블록(유스케이스와 구현체) 교체**로
  대응하라. 분기는 쌓일수록 표준 로직을 오염시키고 요구사항 추적을 불가능하게 만든다.

### 명확성: 인터페이스는 함수가 아니라 계약이다

- 공개 타입의 모든 필드에 의미와 제약, 예시를, 모든 함수에 반환값과 발생 가능한 에러를
  JSDoc으로 기술하라. "타입 정의만 보고 연동 코드를 쓸 수 있는가"가 합격선이다.
- 계약(공개 인터페이스)을 구현과 분리된 패키지로 관리하라.
- 계약 변경 커밋에는 변경 내용과 이유(요구 출처), 설계 의도를 남겨라. Git이 계약서이자 히스토리북이 된다.
- 연동 문서는 계약 코드에서 자동 생성하라. 손으로 관리하는 문서는 반드시 낡는다.

## 상황별 워크플로

### A. 신규 SDK를 설계할 때

1. 핵심 유즈케이스를 나열하고 80%에 해당하는 공통 시나리오를 식별한다 (references/api-design.md)
   verify: 대표 시나리오가 고수준 API 3~5줄로 끝나는가
2. 의도 기반 고수준 API와 escape hatch용 저수준 API의 경계를 정한다 (references/api-design.md)
   verify: 고수준으로 안 풀리는 요구를 저수준 조합으로 풀 수 있는가
3. 계약을 타입+JSDoc으로 명세한다(성공 응답과 에러까지) (references/contract-and-docs.md)
   verify: 문서 없이 타입 정의만 보고 연동 코드를 쓸 수 있는가
4. 변경의 원인 기준으로 계층을 나누고 의존성을 역전시킨다 (references/architecture.md)
   verify: 인터페이스 변경과 정책 변경, 기술 교체가 각각 한 계층만 건드리는가
5. 진입점 런타임 검증과 trace 로깅을 설계에 포함한다
   (references/contract-and-docs.md '런타임 검증 계층' 절, references/stability-and-monitoring.md)
   verify: 잘못된 입력에 필드 단위 에러가 나오는가, 흐름을 식별자 하나로 추적할 수 있는가

### B. 공개 API를 추가하거나 변경할 때

1. 하위 호환성 판단이 최우선이다: 기존 연동 코드가 깨지는가?
   파라미터 추가는 optional로, 의미 변경과 삭제는 새 API 추가 + 기존 deprecate 유지로 대응한다.
2. 변경 내용과 이유, 설계 의도를 계약 변경 기록(커밋)으로 남긴다
   (references/contract-and-docs.md 'Git을 계약서로' 절).
3. 런타임 검증 스키마와 자동 생성 문서가 함께 갱신되는지 확인한다.
4. 배포 후 연동 주체별 성공률과 환경별 성공률로 이상 여부를 확인한다
   (references/stability-and-monitoring.md).

### C. 특정 고객 전용 요구가 올 때

1. 표준 코드에 고객 식별 분기를 넣지 않는다.
2. 요구가 속한 계층을 식별한다: 검증(인터페이스)인가, 정책(도메인)인가, 기술(외부 서비스)인가.
3. 그 계층의 블록만 교체한 커스텀 구성을 만든다. 표준 구성은 그대로 두고,
   조립 시점에 해당 고객만 커스텀 블록을 쓰게 한다 (references/architecture.md '고객 커스텀은 블록 교체다' 절).

### D. SDK 장애와 버그를 분석할 때

1. 환경부터 특정한다: 어떤 브라우저나 웹뷰인가? 입력값의 실제 타입은? 호출 빈도는?
   SDK 버그의 다수는 "예상 밖 환경과 입력, 호출 패턴"에서 온다.
2. trace id로 시작 지점부터 실패 지점까지 구간을 좁힌다.
3. 수정 후 반드시 질문한다: 같은 유형의 사고를 개인의 주의가 아니라
   **구조**(런타임 검증, 인터페이스 설계, 모니터링)로 막을 수 있는가.

각 단계의 상세는 references/stability-and-monitoring.md '장애 대응 루틴' 절을 따른다.
